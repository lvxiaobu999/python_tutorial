# 作业审查技能（review-homework）

审查用户在 `projects/` 下完成的练习代码，给出反馈并直接优化。

## 何时使用

- 用户说「帮我审查 / 检查 / 看看」某个练习文件或作业。
- 用户提到「完成了 XX 作业」，想得到反馈。

## 步骤

1. **定位并通读文件**
   - 用户没给完整路径时，用 `find` 在 `projects/` 下按文件名搜索。
   - 通读全文，区分「教程示例代码」和「作业部分」（通常有 TODO / 练习标记），只审查作业部分。

2. **先运行一遍**
   - 审查前先 `python <文件>` 跑通，记录实际输出，和文件里注释的「期望输出」对照。
   - 有报错就先按 AGENTS.md 规则定位原因、讲清原理；没报错再进入优化环节。

3. **逐题对照要求审查**，按三层检查：
   - **功能正确性**：输出是否符合期望。
   - **是否符合题目要求**：题目明确指定的写法（如「用 sum/len」）没有遵守，算未完成要求，要改。
   - **可优化点**：明显的反模式、重复造轮子、兼容性隐患、PEP 8 风格问题、类型注解缺失或不统一。

4. **发现可优化的逻辑，直接优化，不要只列建议**
   - 这是本技能的核心规则：用户授权过「需要优化就直接改」，不要把问题列成清单等用户自己动手。
   - 每处修改必须讲清「原来的写法有什么问题 + 为什么新写法更好」，让用户从 diff 中学到东西；关键修改可在代码里加一行注释说明原因。
   - 优化幅度要克制，这是学习代码：
     - 优先改：题目明确要求的、明显更简洁/更 Pythonic 的、有兼容性隐患的（如类体内裸名自引用类型注解）。
     - 保留不动：学习者自己的解题思路、刻意的练习性写法（除非与题目要求冲突）。
     - 不做：大规模重构、超出本章节知识点范围的炫技写法。

5. **改完必须重新运行**
   - 重新 `python <文件>`，确认所有输出与优化前一致（除非修改目的就是修输出）。
   - 有测试/验证注释的，逐条对照期望输出。

6. **汇报格式**：先说结论（哪些对了、功能是否全部正确），再逐条列优化点（位置 + 原因），最后贴运行验证结果。

## 常见优化点参考（面向 Python 学习仓库）

- `for` 循环手动累加 → `sum()` / `max()` 等内置函数。
- `len(x) == 0` → `not x`；`len(x) > 0` → 直接用 `x`（真值测试）。
- 多余括号：`if (condition):` → `if condition:`。
- 索引取值 `a[0], a[1]` → 元组解包 `x, y = ...`。
- 类体内 `-> ClassName` 裸名自引用注解 → 字符串 `-> "ClassName"`（Python 3.13- 会 NameError）。
- 顶级定义之间不足两个空行（PEP 8）。
- 类型注解缺失或不统一：审查时**顺手补全**参数和返回值的注解，风格与本章演示代码保持一致（自引用类名加引号）——注解本身就是学习内容的一部分，补全时在汇报里点一句，让学习者注意到这个习惯。

## 注意事项

- 始终遵守 AGENTS.md：中文交流，解释优先于给答案——「直接优化」不等于「只贴答案不解释」。
- 审查的是学习成果，反馈里先肯定用对的地方，再谈优化。
- 如果作业有错导致输出不对，先讲清根因，修复思路引导为主，用户明确要求时才直接改。
