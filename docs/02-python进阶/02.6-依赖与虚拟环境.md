# 02.6 · 依赖与虚拟环境

> 练习代码：[01-环境体检.py](../../projects/02-python进阶/02.6-依赖与虚拟环境/01-环境体检.py)

## 核心概念

- **虚拟环境解决隔离问题**：没有隔离时项目 A 要 pytest 8、项目 B 要 9，装哪个都会弄坏另一个；虚拟环境 = 每个项目一个独立的 `site-packages`（本仓库的就是 `.venv/`）。
- **pyproject.toml 是「意图」，uv.lock 是「事实」**：前者写约束（`pytest>=9.1.1`），后者记录解析结果（`pytest==9.1.1` + 传递依赖的精确版本 + 哈希）。
- **可复现构建**：uv.lock 提交进 git，同事或 CI 跑 `uv sync` 就能装出一模一样的环境；删掉 lock 重新解析 = 版本漂移。
- **dependencies vs dev 组**：运行时依赖放 `[project] dependencies`；pytest/ruff 这类只有开发者要用的放 `[dependency-groups].dev`（`uv add --dev`），不污染生产。
- **`uv run` 是推荐入口**：执行前自动确保环境已同步，且保证用的是本项目 `.venv` 里的解释器。
- **传递依赖**：`uv add pytest` 时，iniconfig/pluggy 等「依赖的依赖」由解析器自动写进 lock 并装好，`uv tree` 能看出谁带进来了谁。

## 关键代码

```bash
uv run python -c "import sys; print(sys.executable)"  # 体检：路径含 .venv 才算活在虚拟环境里
uv add --dev ruff        # 开发依赖，进 [dependency-groups].dev
uv tree                  # 树状看依赖：pytest → colorama/iniconfig/pluggy/…
uv sync                  # 按 uv.lock 精确复原环境（新机器 / CI 第一步）
uv lock --upgrade        # 有意升级时才重新解析 lock
```

```text
[project]
dependencies = ["pytest>=9.1.1"]          # 意图：约束（>=）

[dependency-groups]
dev = ["pytest>=9.1.1", "ruff>=0.17.3"]   # 只有开发者需要

# uv.lock 里则是事实：pytest==9.1.1 这类精确版本 + 哈希，要提交进 git
```

## 常见坑

- **绕过 uv 直接 `pip install` 装到全局**：本仓库红线；应急用 `uv pip install` 也只装进项目环境，但常规操作是 `uv add`。
- **改了 pyproject.toml 手写依赖却没跑 `uv lock`/`uv sync`**：`uv run` 会自动同步兜底，但直接用 `.venv` 里的 python 就不会。
- **把 ruff/pytest 写进 `[project] dependencies`**：别人装你的包会多装一堆没用的东西，工具类依赖放 `--dev`。
- **删 uv.lock「解决」依赖冲突**：冲突信息很有价值，该用 `uv tree` 找出是谁带进来的。
- **把 `.venv` 提交进 git**：体积大且平台相关（Windows 是 `Scripts\`、Linux 是 `bin/`），拿到 pyproject + lock 跑 `uv sync` 就能复原，`.gitignore` 忽略它。
- **在仓库根目录跑 `uv run`/`uv tree`**：uv 从当前目录逐级向上找 pyproject.toml，根目录没有就落到全局 Python 或直接报错——先 `cd projects\02-python进阶`。
