# 03.6 · 错误处理：状态码 + 错误详情

> 练习代码：[06-错误处理.py](../../projects/03-fastapi基础/03.6-错误处理/06-错误处理.py)

## 核心概念

- **API 出错时客户端靠两样东西理解发生了什么**：状态码（给机器读的契约）+ 错误详情（给人看的解释）。422 校验错误是 Pydantic 自动抛的，这一章管剩下的主动报错。
- **`HTTPException` 覆盖 90% 场景**：`raise`（不是 return）立即中断请求处理，FastAPI 把它转成对应状态码的 JSON 响应 `{"detail": ...}`；detail 也可以是 dict，方便前端做结构化提示。
- **自定义异常 + 全局处理器**：业务错误先定义异常类（`class BookNotFoundError(Exception)`）再 raise——含义自解释；`@app.exception_handler(XXX)` 统一翻译成响应。抛错处不用关心状态码和格式，格式要改只动处理器一处。
- **`responses` 参数把错误写进文档**：`responses={404: {"description": "书不存在"}}` 不改变行为，只让 /docs 显示「这个接口可能返回什么错」。
- **反模式：200 里报错**：返回 `{"error": ...}` 但状态码 200 → 客户端必须解析 body 才知道成败，HTTP 语义作废。

## 关键代码

```python
class BookNotFoundError(Exception):
    """业务专属异常：含义自解释，抛的时候不用记状态码。"""

@app.get("/books/{book_id}")
def get_book(book_id: int) -> dict:
    if book_id not in fake_books:
        raise HTTPException(status_code=404, detail=f"book_id={book_id} 不存在")
    return fake_books[book_id]

@app.exception_handler(BookNotFoundError)
async def book_not_found_handler(
    request: Request, exc: BookNotFoundError          # 签名固定：两参数都要写
) -> JSONResponse:
    return JSONResponse(
        status_code=status.HTTP_404_NOT_FOUND,
        content={"message": f"第 {exc.args[0]} 号书不存在"},
    )
```

## 运行结果

- `/books/1` → 200；`/books/99` → 404 + `{"detail": "book_id=99 不存在"}`；
- `/library/99` → 处理器统一转成 404 `{"message": "第 99 号书不存在"}`；
- /docs 观察点：`/catalog/{book_id}` 多了 404 响应说明；把 200 / 404 / 422 各触发一次——这就是期末大作业的验收路径。

## 常见坑

1. **`return HTTPException(...)` ❌**：必须 `raise`。return 只会把它原样序列化成一个 200 响应体。
2. **异常处理器签名固定**：`(request: Request, exc: 你的异常)`，两个参数都要写。
3. **204 不能有响应体**：`status_code=204` 且函数返回 `None`，别想再捎带数据。
4. **detail 忘了写**：客户端只看到干巴巴的状态码，排查全靠猜。
5. **业务错误选码别用 422**：422 是 FastAPI 自动校验的地盘（类型错/缺字段）；请求格式合法、坏在业务规则的用 400（练习 `price_too_high_handler` 注释里写的选择理由）。
