# 04.4 · 后台任务与队列（BackgroundTasks）

> 练习代码：[04-后台任务.py](../../projects/04-fastapi进阶/04.4-后台任务与队列/04-后台任务.py)

## 核心概念

- **问题**：发邮件、写审计日志这类「用户不用等结果」的活，直接写进路由 = 用户干等 3 秒。
- **BackgroundTasks**：`tasks.add_task(函数, 参数...)` 只是**登记**；FastAPI 在响应发送完之后，由同一进程顺手执行。多个任务按登记顺序依次跑，不是并发。
- **与 yield teardown 的分工**：都是「请求后逻辑」——yield 依赖管**本请求资源**的清理，BackgroundTasks 管**响应完用户之后**干活。
- **它的天花板 = Celery 的存在理由**：BackgroundTasks 是进程内的待办清单，任务住在内存——重启即丢、无记录、无重试。要「重启不丢、失败重试、多机分担」，得把任务写进 Redis / RabbitMQ 这样的 broker，由独立 worker 领取——那是 Celery。

## 关键代码

```python
def send_notification(to: str, book_title: str) -> None:
    time.sleep(3)                       # 慢活：只有「后台」在等，用户不等
    print(f"通知已发给 {to}：《{book_title}》")

@app.post("/books-fast")
def create_book_fast(title: str, to: str, tasks: BackgroundTasks) -> dict:
    tasks.add_task(send_notification, to, title)   # 传函数本身，不是调用它！
    return {"message": "图书已创建，通知正在后台发"}
```

## 运行结果

- /docs 对比：`/books-slow` 转 3 秒才响应；`/books-fast` 秒回；
- 终端观察：两条 print 出现在响应**之后**（晚半拍），顺序 = add_task 的登记顺序。

## 常见坑

1. **add_task 写成调用**：`tasks.add_task(send_notification(to, title))` 是当场执行、把返回值 None 登记进去——任务等于没排上。要传**函数本身 + 参数列表**。
2. **async def 里 time.sleep 卡死全局**：事件循环被同步阻塞，所有接口一起瘫痪。慢活写进 `def` 路由（FastAPI 丢线程池）或改用 `asyncio.sleep`。
3. **TestClient 测不出时差**：它会等后台任务跑完才返回——「先回话再干活」要起真服务用 `curl -w "%{time_total}"` 看。
4. **别把 Celery 的特性安到它头上**（思考题真实踩过）：「任务存 Redis、重启不影响执行」是 Celery；BackgroundTasks 重启就丢，两者本质分界在「任务住在哪个进程」。
